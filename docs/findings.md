# 125B MoE を 16GB RAM・8GB GPU で動かす — 測定の記録

Qwen3.8-Flash-Next（総 125B・活性 6B の MoE、Unsloth の UD-Q4_K_XL で 111GB）を、RAM 16GB・VRAM 8GB の家庭用 PC で
llama.cpp を改造して動かした記録。数字はすべてこの PC での実測で、推定の値はそう書いてある。

## 環境

| | |
|---|---|
| CPU | Core i7-11700（8 コア 16 スレッド、PL1 65W） |
| RAM | DDR4-3200 8GB × 2 |
| GPU | GeForce RTX 3060 Ti 8GB |
| SSD | NVMe 1TB（CFD PG3VNF、読み出し実測 約 4.8GB/s） |
| OS | Windows 11 Home |
| llama.cpp | b11361（commit a4cb4c61f）を GCC（w64devkit）で共有ライブラリとしてビルド、CUDA バックエンドは同じ版の配布バイナリ |

モデルの内訳: 48 層、routed expert は 512 個から 10 個を選ぶ（＋共有 expert 1 個）。routed expert が 77GB
（1 トークンで 1.5GB 読む）、n-gram 埋め込み（`per_layer_token_embd`）が 28.8GB、残り 5.7GB は GPU に置く。
起動は `-ngl 99 -ot "\.ffn_(gate|up|down)_exps\.=CPU,per_layer_token_embd=CPU" --no-repack`。

## 1. 何が遅いのかを測る

まず expert の先読み（`common/expert-prefetch.cpp`、ルーティング結果のコールバックで選ばれた expert のスライスを
ワーカー 8 本が `PrefetchVirtualMemory` で読み、ページに触れてワーキングセットに入れる）を入れ、ワーキングセットに
ハード上限 9GB を付けた状態から始めた。1 トークンは約 0.3 s で、そのうち「選ばれた expert がそろうまで」（fetch）が
0.18 s を占め、ワーカーを 8→12 本に増やしても縮まなかった。

診断用の計測（`LLAMA_EXPERT_PREFETCH_DIAG=1`）を足して、1 トークンを分解した。

- 読む 36.9 万ページのうち、ワーキングセットに既にあるのは平均 76%。残りは 1 トークンあたり約 9 万回のページフォールトで入れていた。
- フォールト 1 回の時間はワーカー数とともに増えた（1 本 2.2 µs、2 本 2.5 µs、8 本 5.4 µs、16 本 7.6 µs）。取り合いが起きている。
- SSD からの読み込みは 1 トークン約 250MB だが、1 回 300KB 前後の細切れで、1 回に 0.6〜1 ms かかっていた（キュー深さ 1〜1.3）。

つまり「必要な expert を 4KB ページ単位でワーキングセットに入れる」こと自体が遅く、SSD の帯域も生かせていなかった。

## 2. GPU がデコード中に省電力状態に落ちる

GPU 側の時間を見ると、同じ回答の中で 1 トークン 0.03 s と 0.14 s の 2 つの状態を数秒おきに行き来していた。
nvidia-smi を 0.1 秒刻みで記録すると、デコード中の GPU は P2（メモリ 6800MHz）・P3（5000MHz）・P5（810MHz）・
P8（405MHz）を渡り歩いていた。デコードでは GPU の仕事が細切れで負荷率が低いので、ドライバがメモリクロックを
落とす。GPU 側の処理はメモリ帯域で決まるので、P5 では 4〜5 倍遅くなる。

1 ワープだけの空回りカーネル（PTX を nvcuda.dll に JIT させる）を流し続けると P2・1935MHz に張り付いたが、
速度は逆に 2.7〜3.6 → 1.7 tok/s に落ちた。**Windows（WDDM）では、別のストリームに出したカーネルも並行には走らない**。
10 µs のカーネルの往復時間は、単独で 167 µs、別ストリームに 2 ms の空回りカーネルが 2 本並んでいると 3 ms だった。

そこで空回りを流すのを「ルーティング結果が出てから MoE 出力まで」、つまり CPU が expert を計算していて GPU が
完全に空いている間だけにした（1 本 300 µs、1 本ずつ）。本来の GPU の処理が待つのは最大 1 本分。GPU は P2 に
張り付き、GPU 側の時間は 1 トークン平均 0.08 s 前後から 0.022 s になった。代わりに生成中の GPU の消費電力が
35〜45W 増える（アイドルに戻ると P8 に落ちる）。管理者権限やドライバ設定の変更は要らない（`LLAMA_GPU_KEEPALIVE`）。

## 3. 自前の expert キャッシュ

ページフォールトをやめ、expert を自分で管理するキャッシュに置き換えた。

- **読み込み元**: expert だけを抜き出したコピー `experts-dense.bin`（77GB、`tools/densecopy.cpp`）。
  層×expert ごとに gate・up・down のスライスを並べ、すべて 4KB 境界にそろえる。
  バッファなしで読み書きするので、このファイルにはセクションが一度もできない。
  Windows では、セクション（ファイルマッピング）があるファイルへのバッファなし読みは 1 本ずつに詰まる
  （別のプロジェクトで突き止めた。llama.cpp は GGUF を mmap しているので、元のファイルからは並列に読めない）。
- **置き場**: ロックした私有メモリ 7.37GB（層あたり 49 expert 分。10/6 からは 9.03GB・60 個分、9 章）。unit（1 層の 1 expert）の大きさが 3 種類あるので、
  大きさごとに LRU を持つ。外れたら 1 スライス 1 回の `ReadFile`（バッファなし、0.9〜1.7MB）をワーカー 8 本で読む。
- **計算側への渡し方**: ggml-cpu の MUL_MAT_ID に「expert のデータの在りか」を問い合わせる口
  （`ggml_cpu_set_expert_data_fn`）を足した。計算スレッドは読み込み中のスライスを WaitOnAddress で待つ。
  キャッシュに無いものは従来どおり mmap を読むので、どこで失敗しても結果は正しい。
- **プロンプト**: 32 トークン以上のバッチは GPU 側で計算される（op offload）ので、従来どおり mmap から流す。
- **メモリ**: ワーキングセットは「キャッシュ＋2GB」（ハード上限）を自分で設定する。合計は従来の 9GB と同じ。

結果: キャッシュのヒット率 78%、外れは 1 トークン約 330MB を 1MB ずつ読み、fetch 中の SSD は約 3.5GB/s 出る。
fetch は 0.183 s → 0.097 s になった。10 問・約 3600 トークンの連続運転でも出力は一致し、空き RAM は最小 3.9GB だった。

置き換え方針は、記録したルーティング（3594 トークン）でシミュレーションして決めた（`analysis/cachesim.py`）。
7.37GB のとき、LRU 73.6%、SLRU 74.7%、ARC 73.5%、LFU は LRU より低く、未来を知っている場合（Belady）でも約 86%。

## 4. 次の層の expert を先読みする

計算グラフに「層 N の FFN 入力 × 層 N+1 のルーター行列」のノード（`ffn_moe_pred-N`）を足し、GPU に計算させて
512 個の値だけを受け取る（1 トークンあたり 2.5〜3 ms）。ゲートはソフトマックスでバイアスが無いので、上位 k は
ロジットの上位 k と同じになる。

- 再現率: 上位 10 個で実際の 59〜75%、上位 16 個で 70〜89%。キャッシュに無かった expert に限ると、上位 16 個で 59〜68%。
- 予測した expert のうちキャッシュに無いものを、本命の読み込みより低い優先度で読む。先読みした unit は LRU の冷たい端に
  置くので、外れなら真っ先に追い出される。

SSD が律速なので、読みすぎると本命の読み込みの邪魔をする。3 問ベンチ（3 回の合計時間）:

| 先読み | 外れ/トークン | 読み込み/トークン | 3 問 |
|---|---|---|---|
| なし | 109 | 342MB | 70.2〜70.4 s |
| 上位 8（ワーカー無制限） | 67 | 491MB | 68.7 s |
| 上位 8（先読みはワーカー 2 本まで） | – | – | 67.4 s |
| 上位 12（同 2 本） | – | – | 69.2 s |
| 上位 16（ワーカー無制限） | 42 | 789MB | 73.7 s |

既定は上位 8・ワーカー 2 本（`-Predict 8 -PredictWorkers 2`）。

## 5. 読み込み済みの expert から先に計算する

MUL_MAT_ID は expert を番号順に計算するので、番号の若い expert が外れだと全スレッドがそこで止まる。準備済みかを
問い合わせる口（`ggml_cpu_set_expert_ready_fn`）を足し、各スレッドが読み込み済みの expert を先に片付けるようにした
（expert ごとの作業カウンタがあるので、スレッドごとに順番が違っても正しく分担できる）。効果は +2〜3%
（1 トークン 0.165 → 0.161 s）。読み込み完了から MoE 出力までの約 1 ms/層は、gate → up → down が別の演算で、
その後に GPU への転送と同期が続く構造的な部分で、並べ替えでは縮まない。

## 6. 計測の落とし穴: ログの書き出しが 2 割を食っていた

1 トークンごとの統計行を stderr に直接書いていたところ、1 行に数 ms かかっていた（Start-Process でファイルへ
リダイレクトした stderr）。統計行は最終層の MoE 出力のコールバックの中で書いていたので、「その他」や「グラフの末尾」が
30〜60 ms に膨らんで見え、しばらく原因を探し回った。

| | 3 問の所要 |
|---|---|
| 統計行を stderr に直接書く | 83.5 s |
| 統計行なし | 70.1 s |
| 統計行をバッファに貯め、1 秒ごとにまとめて書く | 70.3 s |

切り分けには、decode の入口・出口の時刻（`LLAMA_DECODE_TIMING=1`）と、グラフ末尾の各ノードの完了時刻
（`LLAMA_EXPERT_PREFETCH_OUTTIME=1`）を同じ時計で並べた。

## 7. 観測するノードを GPU から CPU に移す（+5%）

ggml のスケジューラは、コールバックで観測したノードの直後に必ず GPU を同期させる（`ggml_backend_sched_compute_splits`）。
キープアライブの窓の終わりと時間計測のために各層の「MoE 出力」（GPU 上で expert の出力を合算するノード）を観測していたので、
GPU の処理が 1 層ごとに途中で 1 回止まっていた。観測を CPU 上の最後の MoE ノード（down の行列積、`ffn_moe_down-N`）に移すと、
窓も計測も同じように取れて GPU の同期が 1 層 1 回減る。1 トークン 0.160〜0.165 s → 0.153〜0.154 s、出力は一致。

## 8. 短いプロンプトもキャッシュ経由に（プロンプト処理 2 倍）

32 トークン未満のプロンプトは、CPU で計算するのにキャッシュを通らず、mmap のページフォールトで 2〜4 t/s しか出ていなかった
（16〜28 トークンで 1 層あたり平均 70〜93 個の expert を使う）。これもキャッシュ経由の直接読みにした。デコード用の中身を
守るため、プロンプトの外れは LRU の冷たい端に置き、今の層の unit と読み込み中の unit は追い出さない。次の層のプロンプトの
外れは前の層のプロンプト分を真っ先に追い出すので、デコード用の中身はほとんど残る。24〜28 トークンで 3.5〜4.4 → 8.1〜8.5 t/s。

さらに、GPU 経路は 1 バッチごとに全 expert（約 75GB）を GPU に送るので、プロンプトの長さによらず 1 回 20 秒前後かかる。
CPU と GPU の分かれ目（`GGML_OP_OFFLOAD_MIN_BATCH`、CUDA バックエンドも同じ変数を読む）を変えて測った:

| プロンプト | GPU 経路（閾値 32） | CPU＋キャッシュ経路 |
|---|---|---|
| 65 トークン | 9.9 s | 6.5 s |
| 128 | 15.2 s | 10.1 s |
| 246 | 20.1 s | 14.2 s |
| 476 | 21.5 s | 17.4 s |
| 965 | 29.1 s | 25.6 s |
| 1831 | 35.1 s | 39.0 s |

交差点は約 1300 トークンなので、閾値を 1280 にした。CPU で計算するプロンプトは GPU で計算したときと数値がわずかに違うので、
その後の回答が変わることがある（10 問中 3 問）。

## 9. 大きなプロンプトの間だけキャッシュを手放す

キャッシュに 7.4GB を割いた分、mmap 側に残るワーキングセットが 9GB から 2GB に減り、GPU 経路のプロンプト処理が遅くなっていた
（3551 トークン: mmap 側 9GB 73.7 t/s、3GB 68.2、2GB 64.9、1GB 59.4、0.6GB 49.5 t/s）。ワーキングセットの上限は合計に
かかるので、GPU 経路のバッチの間だけキャッシュの冷たい部分を decommit すれば、その分を mmap 側が使える。
層 0 のルーティングで判定し（最終層は出力の 1 行だけを計算するので、途中で判定すると往復してしまう）、次に CPU 側の処理が
来たら確保し直す。手放すのに 0.2 s、戻すのに 1.8 s（3.5GB）。

これで配分を「キャッシュ 9.0GB＋mmap 側 0.6GB（GPU バッチ中は 3.5GB を手放す）」にでき、デコードは速く、長いプロンプトは
今までどおりになった（3551 トークン: 手放さないと 49.5 t/s、3.5GB 手放すと 65.5 t/s）。

## 10. 試してやめたこと

- **常時のキープアライブ**: WDDM でカーネルが並行しないため 2.7〜3.6 → 1.7 tok/s。
- **先読み上位 12・16 個**: 無駄読みで SSD を食い、得がない。
- **LFU・ARC**: シミュレーションで LRU 以下。SLRU は +1 ポイントで、未実装。
- **MTP（投機的デコード）**: MTP ヘッドは別配布（2.6GB 以上）で、このビルドは本体の埋め込み・出力層を借りる版に未対応。
  VRAM は 8GB 中 7.4GB 使用済みで載らない。連続 2 トークンの expert の和集合は層あたり 15.4 個（1.54 倍）なので、
  受理率 0.6〜0.7 でも +6〜12% 程度と見積もった（推定）。

## 11. 残っている課題

- 残りの律速は、SSD（外れの読み込み）と RAM の帯域（1 トークンで 1.5GB の expert を CPU が読む。DDR4-3200 の
  2 チャネルで 35 ms 前後、推定）。大きく縮めるには読む量を減らすしかない。
- 1280 トークン以上のプロンプトの GPU 経路は、まだ mmap 経由で読んでいる。`experts-dense.bin` からの直接読みにすれば速くなる見込み。
- サーバーはプロンプトの末尾数トークンを別のバッチに分ける（コンテキストのチェックポイント用）。そのぶん 1 パス余計にかかる。

## 既知の問題

- **キープアライブのカーネルが終わらず、サーバーが止まった（2 回、修正済み）**。1 回目は起動直後、2 回目は約 22 時間ぶりの
  リクエストの最初のデコードで、18 時間止まっていた。デバッガ（cdb、noninvasive）で全スレッドのスタックを取ると、本体の
  スレッドは `cudaStreamSynchronize` で待ち続け、キープアライブのスレッドは自分の空回りカーネルの完了を待っていた。
  WDDM では別ストリームでも順番待ちになるので、空回りカーネルが終わらないと本体の処理も進まない。
  空回りの終わりを `%globaltimer`（GPU の ns 時計）で判定していたのを、`%clock64`（SM の周期カウンタ）のサイクル数に変えた。
  時計の値がどう振る舞っても必ず有限時間で終わる。あわせて、空回りカーネルが 3 秒以上終わらないとログに書く見張りを入れた。
  長い休みの後に `%globaltimer` が飛ぶという原因は未確認（5〜95 秒の休みを挟んだ試験では飛ばなかった）。
- 自前ビルドの exe が終了時に GPU ドライバの中で止まり、強制終了できないことがある（DLL が掴まれたままになり、
  再ビルドに失敗する。使用中のファイルを改名すればビルドできる）。
